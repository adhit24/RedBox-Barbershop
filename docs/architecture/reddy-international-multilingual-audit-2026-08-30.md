# Reddy International WhatsApp + Multilingual — Source Audit Report

Branch: `fix/reddy-international-whatsapp-multilingual`, based on `origin/main` at `36371e9` (PR #53, "barber presence first-turn guard", already merged).

This report classifies every code path that determines (A) sender acceptance, (B) phone normalization, (C) language, (D) foreign routing, (E) deterministic response language — as it stood before this branch, and what this branch did to it.

Classification legend: **KEEP** (unchanged, correct as-is), **REPLACE** (rewritten in this branch), **LEGACY COMPATIBILITY** (unchanged, kept for compatibility, not expanded), **REMOVE LATER** (confirmed dead/unreachable, candidate for future deletion, not touched here).

## A. Sender acceptance (personal vs group/broadcast/non-personal)

- `server/identity/whatsappIdentityAdapter.js:63-70` `hasUnsupportedSenderShape()` — rejects `@`, `broadcast`, `g.us`, `s.whatsapp.net` substrings before a sender ever reaches phone normalization. **KEEP** — untouched, still correct, still the first line of defense.
- `server/services/fonnteWebhookVerifier.js:86` `classifyFonnteEvent()` — real group/broadcast classification (`isGroup`/`is_group`/`@g.us$`/`@broadcast$`/`groupId`), gates `issueAuthenticatedWhatsappEvent`. **KEEP** — untouched.
- `server/services/waInboundGuard.js`'s `classifyInboundEvent()` — the actual admission gate for the live reply pipeline (`handleMessage`). Has **no group/broadcast check at all**; only `fonnteWebhookVerifier.js`'s check (above) has one, and it's wired only into the dormant trust-gated CRM-identity path, not the live pipeline. **PRE-EXISTING GAP, OUT OF SCOPE** — not part of the contract's named file list or objectives (which are about phone internationalization, not group filtering), not touched by this branch. Flagged here for visibility; recommend a separate, dedicated task if the team wants to close it, since it's a materially different piece of work (wiring real classification into the live admission path) with its own regression surface.

## B. Phone normalization

- `server/identity/trustedIdentity.js:9-10` (pre-branch) `LOCAL_PHONE_PATTERN` / `INTERNATIONAL_PHONE_PATTERN` — Indonesia-only (`/^\+?628\d{8,11}$/`), the root cause. **REPLACED** by `server/identity/phoneNormalization.js`'s `normalizePhoneNumber()`, a shared bounded E.164-style digit normalizer (8-15 digits, no leading zero, single optional leading `+`), reused by `trustedIdentity.js`'s `normalizeVerifiedPhone()`.
- `server/services/fonnte.js:111-166` `sendWA`'s outbound normalizer — also Indonesia-only, and actively corrupted foreign target numbers. **REPLACED, in two passes.** Pass 1 (this branch's original commit) fixed the unconditional case: anything not starting with `0`/`62` got `62` blindly prepended, corrupting e.g. a Singapore number into `62` + `6591234567`. Pass 2 (correction round 1) fixed a narrower but still-real case pass 1 left behind: the fallback still prepended `62` onto any bare `8...`-prefixed number, which is ambiguous — several real country codes also start with 8 (Japan 81, Korea 82, Vietnam 84, China 86, Cambodia 855, Bangladesh 880, Taiwan 886), so e.g. Japan's `819012345678` was still being corrupted into `62819012345678`. Now a bare 8-prefix target is left untouched by default; a caller can opt in per-call with `{ assumeIndonesianLocalShorthand: true }` if it specifically knows its target is bare Indonesian shorthand — audited, no current caller needs it (see round-1 correction commit message for the full caller audit). Not named in the contract's audit file list, but required for objective 1's business goal to actually work end-to-end (a reply to an accepted international sender must reach them correctly formatted).
- `server/member-identity.js:3-6` `normalizeMemberPhone` — a third, independent Indonesia-only normalizer, used for CRM/member phone matching. **LEGACY COMPATIBILITY, NOT FIXED** — out of scope: governs member lookup, not WhatsApp acceptance/reply; not named in the contract's file list; touching it risks CRM regressions for existing Indonesian members. Flagged as a follow-up.
- `server/services/waInboundGuard.js:14-16` `normalizePhoneDigits()` (digit-strip only, feeds `senderHash`) and `api/wa/webhook.js`'s `normalizePhone()` (admin-number comparison) — neither is format-biased toward Indonesia; **KEEP**, untouched.

## C. Language

- `api/wa/webhook.js`'s (pre-branch) `hasIndonesianLanguageSignal` / `isForeignLanguage` / `detectForeignLanguage` / `resolveExistingResponseLanguage` — four functions, two different precedence rules (the presence-guard path had a conversation-history fallback; the general path didn't). **REPLACED** — consolidated into `server/agents/reddy/languageResolution.js`, one precedence contract (`resolveResponseLanguage`) used by both paths. `detectForeignLanguage` extended with malay/french/german/spanish detection (chinese/japanese/korean/arabic/turkish/thai/english were already supported); `hasIndonesianLanguageSignal` and the Indonesian-word heuristic are unchanged. `webhook.js` now requires and re-exports from this module rather than defining its own copies.
- Language is confirmed **never derived from phone/country code**, before or after this branch — locked in by `server/test/whatsapp-identity-adapter-v01.test.js:165-181` (pre-existing) and by this branch's `languageResolution.js` functions taking only text/conversation-context parameters (no phone/identity parameter exists to pass).

## D. Foreign routing

- `api/wa/webhook.js`'s `handleForeignBooking` / `handleForeignGeneralQuestion` (english/chinese/japanese/korean/turkish templates via `foreignMsg()`, which already falls back to English for any unmapped language key) — live, tested (`server/test/reddy-knowledge-system-v01.test.js:1311-1488`), triggered by `isForeignLanguage(text)`, never by phone/country code. **KEEP** — untouched; the newly-recognized languages (malay/french/german/spanish) safely degrade to the existing English CTA templates via `foreignMsg`'s existing fallback, by construction.
- `server/whatsapp-ai/services/foreignBookingService.js` (541 lines, its own duplicate `isForeignLanguage`/`detectLanguage` and a full booking-collection state machine) — confirmed **dead code**: not mounted anywhere reachable from `vercel.json`'s routing, and its unreachability is locked in by `server/test/booking-intelligence-v01.test.js:336-340`. **REMOVE LATER** — not touched in this branch (Global Constraint: don't expand or wire in dead code; removing it entirely is a separate cleanup decision for the team, not part of this contract).

## E. Deterministic response language

- `server/agents/reddy/realtimeFactGuard.js`'s `buildSafeStatement` — already branched English vs. Indonesian correctly before this branch. **KEEP** — untouched; already satisfied objective 7's literal bar.
- `api/wa/webhook.js`'s `fallbackReply()` (knowledge-unavailable + generic fallback + all keyword branches), `server/agents/reddy/bookingGuards.js`'s `guardReddyReply` correction text, CRM points-inquiry messages, human-handoff messages — all previously always-Indonesian regardless of `responseLanguage`, even where `responseLanguage` was already in scope. **REPLACED** — each now branches English/Indonesian. Bounded to these two languages deliberately, matching the contract's own test list (30-33, English/Indonesian only) and its "don't translate everything" guidance.
- `server/agents/reddy/bookingGuards.js`'s `PROHIBITED_PATTERNS` / `UNVERIFIED_AVAILABILITY_PATTERNS` (fake-booking-confirmation / unverified-availability claim detection) — was Indonesian-phrase-only, so an English LLM reply making the same false claim wasn't caught. **REPLACED** (extended) — added an English pattern set (`ENGLISH_PROHIBITED_PATTERNS` / `ENGLISH_UNVERIFIED_AVAILABILITY_PATTERNS`), mirroring the same approach `realtimeFactGuard.js` already uses for its own English detection layer.
- `reddyAdapter.js`'s hardcoded-Indonesian `buildPresenceReply` and `BOOKING_COMPLETION_ACK_REPLY` — `buildPresenceReply` is only invoked when `responseLanguage === 'indonesian'` (gated, so it's safe by construction, not by being multilingual). `BOOKING_COMPLETION_ACK_REPLY` is sent unconditionally regardless of language. **LEGACY COMPATIBILITY, NOT FIXED** — out of the bounded scope of this branch's Task 5 (not one of the explicitly named guards in objective 7's list); flagged as a follow-up if the team wants full coverage.
- Business-policy replies (`isHomeService`/`isWedding`/`isOtw`/`isWalkIn` deterministic replies in `api/wa/webhook.js`) — hardcoded Indonesian regardless of detected language. **LEGACY COMPATIBILITY, NOT FIXED** — deliberately out of scope: not named in objective 7's guard list, and the contract explicitly discourages "dozens of hardcoded business-answer templates."
